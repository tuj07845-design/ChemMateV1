# 工具层改造总览

> 适用分支：`dev-langchain-main-angent`
> 读者：要亲手重写 `CMV1/tools/` 的人
> 用法：先读本篇（规则与顺序），再按需翻各模块分册

---

## 一、这套文档怎么用

每个模块一篇，结构固定：

| 小节 | 回答什么问题 |
|---|---|
| 一、定位 | 这个模块在整条链路里的位置，谁调它、它调谁 |
| 二、改造清单 | 哪个文件、哪一行、改什么、风险几颗星 |
| 三、为什么这么改 | 每条结论的证据（引用、调用数、实测报错） |
| 四、操作步骤 | 先做什么后做什么，哪一步可以停下验证 |
| 五、逐块原子拆解 | 每个函数：**为什么需要它 → 输入输出 → 一条条写什么 → 坑在哪** |
| 六、自检清单 | 改完怎么证明没改坏 |

原则：**先讲原因，再拆代码**。看不懂"为什么"就不要动那一行。

## 三、六个冻结契约

这 6 个签名和返回字典的键名，是 agent 层与 tools 层之间唯一的接口。**改签名 = 改 agent**，不在本次改造范围内。

| # | 工具 | 冻结签名 | 成功返回必须含 | 谁在依赖 |
|---|---|---|---|---|
| 1 | `data_get_process` | `(file_path: str) -> dict` | `success` `streams` `blocks` `connections` `block_details` `simulation_status` `file_path` | analyze / draw_mat / report 都在读这些键 |
| 2 | `analyze_process` | `(component=None, change_threshold=0.05) -> dict`★ | `success` `summary` `findings` `component_tracking` `stream_changes` | 模型 |
| 3 | `draw_mat` | `(plot_type, streams=None, stream=None, component=None, block=None, value_field="mole_fraction", title="", export="png") -> dict` | `success` `image_path` `caption` `meta` `warnings` `job_dir` | 模型拿 `image_path` 喂给 report_create 的 image 块 |
| 4 | `report_create` | `(report_type, title, sections) -> dict`★ | `success` `file_path` `report_type` `section_count` | 模型 |
| 5 | `bash` | `(command: str, timeout: int = 60) -> dict` | `success` `stdout` `stderr` `returncode` | 模型 |
| 6 | `path_finder` | `(filename: str) -> dict` | `success` `file_path` | 模型 |

失败返回也必须保留原有关键字（`success=False` + `error` + `message`），因为 `tools_register` 和模型都按这些键判读。

> **表格里写的是模型可见的签名**（`tools_register.py` 中 `@tool` 函数的形参）。带 ★ 的两个，内部实现函数多几个参数：
> `analyze_process` 首参是 `process_data`（数据由缓存取好后传入）；
> `report_create` 还有 `output_path` / `author`。
> 同理 `draw_mat` 的内部实现还有 `process_data` / `matlab_draw_path` / `jobs_root` / `dry_run`。
> 这些由适配层或调用方填充，模型看不到。重写时**保留这些参数**（测试和调试要用），但不要写进 docstring。

## 四、四条通用改造原则

### 原则 1：先删死代码，再谈重写

顺序反了会白干：你花两小时美化一个没人调用的函数，最后发现它整块可以删。

判定死代码的三层证据，缺一不可：

1. **字符串搜索**：`Grep` 全仓库，排除注释后看还剩什么；
2. **AST 扫描**：区分"被 import"和"被调用"（import 只是挂名，`.py` 里 `from x import y` 不等于用了 `y`）；
3. **动态路径排查**：有没有 `getattr(obj, "名字")`、`import *`、`__init__.py` re-export。

本次已经用 AST 扫过全仓库（跳过 `.venv` / `__pycache__`），结论写在各自分册的"改造清单"里。

### 原则 2：格式服从逻辑，别让排版掩盖结构

老代码有两个极端：

- `process_data_get` / `analyze`：**一参数一行**，`return {` 后面每个键之间空一行。一个 40 行的 dict 能撑成 120 行，读的时候眼睛要跳着找。
- `draw_mat` / `report_create`：正常密度，可以当排版参照物。

压缩标准（照 `draw_mat` 的样子）：

- 字典/列表里连续的短项，一行一项，**不空行**；
- 函数之间空 2 行，逻辑段之间空 1 行；
- 一个 `if` 只有一条短语句时，允许合到一行（`if not q: return None`），但**判断和副作用要一眼能分开**。

### 原则 3：契约冻结，内部随便改

重写时只盯三样东西：

- 函数名（外部 import 的名字）；
- 参数名（`tools_register` 用关键字传参，如 `component=`、`change_threshold=`）；
- 返回字典的键名。

函数内部变量名、拆分方式、辅助函数数量，全部自由。

### 原则 4：对拍验证，不靠肉眼

每个模块改完，用**同一份输入**跑旧版和新版，比 JSON。标准四件套：

| 输入 | 期望 |
|---|---|
| 正常 dict | 返回结构完全一致（键、类型、数值） |
| 正常 JSON 字符串 | 同上（验证 `_coerce_process_data`） |
| 坏 JSON / 空串 | `success=False` 且 `error` 文案一致 |
| 上游失败 dict | 短路逻辑一致 |

`draw_mat` / `report_create` 还要加一个"产物检查"：图片文件存在且非 0 字节 / docx 能打开。

## 六、推荐执行顺序

按"能不能本地验证"排序，风险从低到高：

| 顺序 | 模块 | 为什么排这里 | 本地可验证性 |
|---|---|---|---|
| 1 | `analyze` | 纯数据变换，不碰任何外部进程 | ★★★★★ 喂 dict 就能测 |
| 2 | `draw_mat` | 拆表纯逻辑可测；只有最后一步调 MATLAB | ★★★★☆ `dry_run=True` 可跳过 MATLAB |
| 3 | `report_create` | 纯 Python，但要装了库才能渲染 | ★★★★☆ 生成的 docx/pptx 能打开即通过 |
| 4 | `process_data_get` | 每一步都要 Aspen COM，错一步就弹窗 | ★★☆☆☆ 必须有 .bkp 才能测 |
| 5 | `bash` / `path_finder` | 小文件，顺手改 | ★★★★★ |

**不要跳着改。** 前一个模块的对拍没通过，就别动下一个——否则出错时无法定位是哪一层的问题。

## 七、改造前的准备工作

1. **打标签**：`git tag before-tools-refactor`，随时能回滚整个工具层。
2. **确认基准**：跑一次完整链路（`data_get_process` → `analyze_process` → `draw_mat` → `report_create`），把 4 个返回值存成 `baseline.json`，这是对拍基准。
3. **准备样例**：`10万吨环己烷.bkp` 就是现成的 Aspen 样例；MATLAB 路径确认 `CHEMMATE_MATLAB_BIN` 已设置（参考 `draw_mat` 分册）。
4. **一个模块一个提交**：改完 analyze 就 commit 一次，别攒到最后。

## 九、改完后的预期规模（验收口径）

实测基准：2026-10-18，按 `splitlines` 计行。

| 模块 | 当前 | 预期 | 减幅 | 主要来源 |
|---|---:|---:|---:|---|
| `analyze/` | 2026 | ~1300 | -36% | 删 `[qoder 指导]` + 空壳 + 压空行 |
| `draw_mat/` | 1060 | ~1010 | -5% | 删 `process_store` + `tool_spec`；`_lookup_component` 已加三级匹配（+22） |
| `process_data_get/` | 1397 | ~800 | -43% | 压缩排版（536→~280 等） |
| `report_create/` | 885 | ~680 | -23% | `sections.py` 大删 |
| `bash` + `path_finder` | 144 | ~146 | 0 | 只改逻辑，行数基本不变 |
| **合计** | **5656** | **~3900** | **-31%** | |

**这 31% 里，真正的代码行只占一小部分**：

| 成分 | 当前 | 预期 | 说明 |
|---|---:|---:|---|
| 空行 | 1146 | ~500 | 排版压缩，逻辑不变 |
| 注释 | 851 | ~480 | 删施工注释 + docstring 重排 |
| 代码 | 3659 | ~3420 | 删死代码：`process_store` / `sections` 大部分 / `tool_spec` 三件套 |

> **结论：这是“排版与死代码清理”，不是“逻辑瘦身”。** 改完之后函数该有的分支、校验、异常处理一个不少，
> 所以不要用“行数减半”当作成功标准——**能减到 3600–4100 行就是到位了**。

**不在本次范围内的文件**（不要为了凑数字去动它们）：

| 文件 | 行数 | 为何不动 |
