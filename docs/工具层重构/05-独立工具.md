# 05 · 独立工具（bash / path_finder）

> 覆盖 `CMV1/tools/bash_tool.py`（51 行）、`CMV1/tools/path_finder_tool.py`（93 行）
> 两个文件都不属于任何子包，直接放在 `tools/` 下

---

## 一、定位

这两个工具与前面四个模块的区别：

| | analyze / draw_mat / report / process_data_get | bash / path_finder |
|---|---|---|
| 注册方式 | 裸函数 + `tools_register.py` 用 `@tool` 包装 | `bash` 走 `tools_register`；`path_finder` **自己在模块里 `@tool`** |
| 职责 | 业务能力（读数据、算数据、出图、出报告） | 通用能力（执行命令、找文件） |
| 在 agent 里的定位 | 主力 | 兜底 / 前置 |

`cmv1_langchain.py` 的系统提示词写得很明确：

> 用户没给文件绝对路径时，先用 `path_finder` 找文件；
> `bash` 仅在其它工具不够用时兜底，其它情况禁用。

**`bash_tool.py`**

```
tools_register.bash(command, timeout=60)
        ▼
bash_tool.bash(command, timeout)     ← 唯一函数
        ├── 空命令检查
        ├── 黑名单检查
        └── subprocess.run(["powershell", "-NoProfile", "-Command", cmd], cwd=WORK_ROOT)
```

**`path_finder_tool.py`**

```
cmv1_langchain.py: from tools.path_finder_tool import path_finder
cmv1_langchain.py: tools = [..., path_finder]        ← 直接进工具列表，不经过 tools_register
        ▼
path_finder(filename)                ← @tool 装饰后的对象
        ├── _compact_filename()    去空白 + casefold
        └── os.walk(用户主目录)
```

## 三、为什么这么改

### 3.1 `WORK_ROOT` 为什么不能写死

```
WORK_ROOT = Path(r"C:\Users\Fool\Desktop\ChemMateV1工作台").resolve()
```

后果：

- 换一台机器 / 把项目挪个目录 → `cwd` 指向一个**不存在**的路径，`subprocess.run` 直接抛 `FileNotFoundError`，`bash` 工具全废；
- 用户目录不是 `Fool` 时同理。

改成：

```
WORK_ROOT = Path(__file__).resolve().parents[2]
```

`bash_tool.py` 在 `CMV1/tools/` 下：`parents[0]=tools`、`parents[1]=CMV1`、`parents[2]=工作台根`。

和 `report_core._reports_root` / `draw_mat._default_jobs_root` 用同一套思路——**永远不要用 `cwd` 或写死绝对路径**。

### 3.2 编码 bug（已实测，这是本文件最值得改的一处）

`bash()` 里：

```
proc = subprocess.run(
    ["powershell", "-NoProfile", "-Command", cmd],
    ...
    encoding="utf-8",
    errors="replace",
)
```

看起来"统一用 UTF-8"很正确，实际在中文 Windows 上是错的：PowerShell 5.1 的 stdout 默认按**系统 OEM 代码页（GBK / cp936）**输出字节，Python 却按 UTF-8 解码 → 乱码。

**实测矩阵**（本机 Windows 11 + Python 3.13，`subprocess.run(..., encoding="utf-8")` 收 PowerShell 输出）：

| 命令前缀 / 环境 | `echo 中文测试` | `python -c "print('中文测试')"` |
|---|---|---|
| 什么都不设（当前代码） | ❌ 乱码 | ❌ 乱码 |
| `[Console]::OutputEncoding=[Text.Encoding]::UTF8;` | ✅ | ❌ |
| `$OutputEncoding=[Console]::OutputEncoding=[Text.Encoding]::UTF8;` | ✅ | ❌ |
| `chcp 65001 > $null;` | ✅ | ❌ |
| 任一种前缀 + `PYTHONIOENCODING=utf-8` | ✅ | ✅ |
| 任一种前缀 + `PYTHONUTF8=1` | ✅ | ✅ |

**关键认知：两层编码，不能混为一谈。**

1. **PowerShell 自己的输出**（`echo` / `dir` / `Get-ChildItem`）：由 `[Console]::OutputEncoding` 或 `chcp` 决定；
2. **子进程（python.exe）的 stdout**：由 Python 自己按 locale 决定（Windows 上是 cp936），**跟 PowerShell 的设置完全无关**。必须在进程环境里给 `PYTHONIOENCODING=utf-8`（或 `PYTHONUTF8=1`）。

所以单独改哪一层都不够：只设 `[Console]` 只能救 `dir`，救不了 `python script.py`。

> 修正一条早前结论：`chcp 65001` **是有效的**。上次测出"无效"是因为写成了 `chcp 65001; cmd`——`chcp` 自己那行 `Active code page: 65001` 混进了 stdout，看起来像乱码。加 `> $null` 后它与 `[Console]` 写法等价。

**推荐改法**（两层都显式 UTF-8）：

```
proc = subprocess.run(
    ["powershell", "-NoProfile", "-Command",
     "[Console]::OutputEncoding=[Text.Encoding]::UTF8; " + cmd],
    ...,
    encoding="utf-8",
    errors="replace",
    env={**os.environ, "PYTHONIOENCODING": "utf-8", "PYTHONUTF8": "1"},
)
```

为什么不用"删掉 encoding 让它按 locale 解码"：不依赖系统语言（英文 Windows 默认 cp1252，删了 `encoding` 直接坏）；
而且 `tools/` 下的 `.py` 都是 UTF-8，统一口径才不会出现"这个文件里中文正常、那个文件乱码"。

**代价**：如果在 bash 里跑的是**只认 GBK 的老式 exe**，它反而会乱码。这类程序在兜底场景里极少，可以接受。

### 3.3 黑名单为什么只能"防手滑"

```
BLOCK = ("rm -rf", "del /s", "format", "shutdown", "reg delete", "Remove-Item -Recurse")
```

`if bad.lower() in low` 是**子串匹配**，绕过的写法至少有一打：

| 想删东西 | 能不能绕过 |
|---|---|
| `rm -r -f` | ✅ 绕过（黑名单只挡 `rm -rf`） |
| `Remove-Item -r -fo` | ✅ 绕过（只挡 `-Recurse` 全拼） |
| `ri -r`（别名） | ✅ 绕过 |
| `cmd /c del /s` | ✅ 绕过（但 `del /s` 在字符串里，会命中） |
| `& ('Remove' + '-Item') -Recurse` | ✅ 绕过（拼接后不在原文里） |

**结论**：这不是安全边界，是**防模型手滑**的护栏。真正的安全来自：

1. `cwd` 被锁在工作台目录（相对路径操作不会跑到系统目录）；
2. 模型没有恶意（它是被提示词约束的助手，不是攻击者）；
3. 用户可以随时拒绝工具调用。

**改造动作**：保留黑名单，把注释从"禁止的危险命令"改成"**防手滑，不是安全边界**"——避免后来者误以为它是沙箱。

### 3.4 超时后孙进程可能残留

`subprocess.run(timeout=...)` 超时后，Python 会 `kill()` 直接子进程（powershell.exe），但**孙进程**（powershell 启动的 python.exe / matlab.exe）不一定被杀。

后果：一个死循环的 `python train.py` 超时后，进程还在后台吃 CPU。

彻底修法是 `Popen` + `taskkill /PID <pid> /T /F`（`/T` 连子进程树一起杀）。但代码量会翻倍。

**取舍**：当前是"兜底工具"，模型很少用它跑长任务。**本次建议不改**，只在注释里写明这个限制。

### 3.5 为什么 `path_finder` 自己 `@tool` 可以保留

两种注册方式并存确实不统一：

| 工具 | 注册位置 | 原因 |
|---|---|---|
| 其余 5 个 | `tools_register.py` | 需要适配：隐藏 `process_data` 参数、读写缓存、包装返回 |
| `path_finder` | 模块内 `@tool` | 不需要任何适配——入参就一个 `filename`，没有缓存，没有内部参数 |

**保留的理由**：`tools_register` 的价值是"适配"，`path_finder` 不需要适配。硬把它塞进去反而多一层无意义的转发。

**但要在 `tools_register.py` 的文件头注释里写明**："`path_finder` 不走本文件，直接在 `cmv1_langchain.py` 注册"。否则下一个人会在 `tools_register` 里找一个不存在的包装函数。

### 3.6 为什么 `path_finder` 要剪枝

`os.walk(os.path.expanduser("~"))` 在 Windows 上会遍历：

```
C:\Users\Fool\
├── AppData\              ← 几万个小文件（缓存、包元数据）
├── .venv\                ← 项目虚拟环境（几千个 .py）
├── node_modules\         ← 前端依赖（几万个文件）
├── .git\                 ← 仓库对象
└── Desktop\ChemMateV1工作台\10万吨环己烷.bkp   ← 真正要找的
```

搜一个文件可能跑 10~60 秒，其中 99% 的时间花在完全无关的目录。

**剪枝写法**：

```
SKIP_DIRS = {"AppData", "node_modules", ".git", ".venv", "__pycache__", ".cache"}

for root, dirs, files in os.walk(user_home):
    dirs[:] = [d for d in dirs if d not in SKIP_DIRS and not d.startswith(".")]
    ...
```

**注意 `dirs[:] = ...`**：必须**原地修改** `dirs` 列表，赋新列表（`dirs = [...]`）不会影响 `os.walk` 的遍历——这是 `os.walk` 剪枝的经典坑。

**风险**：如果用户真把 `.bkp` 放在 `AppData`（极不可能），会找不到。可以接受。

### 3.7 为什么 `path_finder` 要优先 Aspen 扩展名

现在 `filename="10万吨环己烷"` 会命中**任意**同名文件（`.bkp`、`.txt`、`.lnk` 都有可能）。用户的本意几乎永远是 Aspen 文件。

**改法**：收集所有匹配，返回时按扩展名优先级排序：

```
priority = (".bkp", ".apwz", ".apw", "")
```

先命中 `.bkp` 就立刻返回（保持现在的"早退"行为），否则记住第一个匹配，搜完再返回。

## 五、逐块原子拆解

### 5.1 `bash_tool.py`

#### `bash(command, timeout=60) -> dict`

**为什么需要**：给模型一个"最后手段"。其它工具覆盖不到的临时检查（`dir`、`python script.py`、`type file.txt`）用它。

**返回契约**：`{"success", "stdout", "stderr", "returncode"}`。

**原子步骤**：

1. **空命令检查**：
   `cmd = (command or "").strip()`；`if not cmd: return {"success": False, "stdout": "", "stderr": "命令为空", "returncode": -1}`
   为什么 `(command or "")`：模型可能传 `None`，直接 `.strip()` 会 `AttributeError`。

2. **黑名单检查**：
   `low = cmd.lower()`；逐个 `bad` 比 `bad.lower() in low`；命中 → 返回 `stderr=f"禁止命令: {bad}"`。
   为什么双向 `lower()`：`BLOCK` 里有大小写混合的项（`"Remove-Item -Recurse"`），命令也可能大小写混合。

3. **执行**：
   ```
   proc = subprocess.run(
       ["powershell", "-NoProfile", "-Command", cmd],
       cwd=str(WORK_ROOT),
       capture_output=True, text=True,
       timeout=timeout, encoding="utf-8", errors="replace",
   )
   ```
   参数逐个解释：
   - `-NoProfile`：不加载用户 profile，避免自定义函数/别名污染；
   - `cwd=WORK_ROOT`：相对路径都落在工作台里；
   - `capture_output=True`：同时抓 stdout / stderr；
   - `text=True`：返回 str 不是 bytes；
   - `timeout`：防死循环；
   - `errors="replace"`：解码失败用 `�` 代替，不抛异常（但**正确做法是让编码本身对**，见 3.2）。

4. **包装返回**：
   ```
   return {
       "success": proc.returncode == 0,
       "stdout": (proc.stdout or "")[:8000],
       "stderr": (proc.stderr or "")[:4000],
       "returncode": proc.returncode,
   }
   ```
   为什么截断：模型上下文有限，一个 `dir /s` 能输出几 MB，不截断会挤爆 prompt。
   为什么 stderr 限额更小（4000）：错误信息通常短，且模型只需要前几行定位。

5. **异常处理**（两个分支）：
   - `TimeoutExpired` → `stderr=f"超时({timeout}s)"`、`returncode=-1`
   - 其它 `Exception` → `stderr=str(e)`、`returncode=-1`

**坑**：

- `success` 只看 `returncode == 0`。PowerShell 里"命令内部报错"但退出码是 0 的情况很多（比如 `Get-Item 不存在的文件` 会写错误流但退出码 0），所以 `success=True` 不代表命令真的成功——**模型要学会看 stderr**。
- 截断发生在**字符**层面，可能把一个多字节字符切成两半。`errors="replace"` 只在解码阶段起作用，截断在之后。实际影响很小（模型能容忍末尾一个 `�`）。

### 5.2 `path_finder_tool.py`

#### `_compact_filename(value) -> str`

**为什么需要**：用户手打的文件名经常带多余空格，比如 `"10万吨 环己烷.bkp"` 实际叫 `"10万吨环己烷.bkp"`。

**写法**：`"".join(str(value).split()).casefold()`

- `.split()` 不带参数 → 按任意空白切分并丢弃空串；
- `.casefold()` 比 `.lower()` 更彻底（处理德语 ß 等，虽然这里用不上，但没坏处）。

#### `path_finder(filename) -> dict`

**为什么需要**：模型拿不到绝对路径时，先用它把文件名变成路径，再喂给 `data_get_process`。

**返回契约**：

```
成功: {"success": True, "filename": 输入值, "file_path": 绝对路径}
失败: {"success": False, "filename": 输入值, "file_path": None, "error": "没有找到指定的 Aspen 文件"}
```

**原子步骤**：

1. **删掉那行裸 `...`**（当前第 20 行）。它是 Ellipsis 表达式，合法、无害、**也不 return**，纯粹是历史残留——但读代码的人会以为"函数体被省略了"，非常误导。
2. **确定搜索起点**：`user_home = os.path.expanduser("~")`。
3. **准备两种匹配键**：
   - `requested = str(filename).casefold()` —— 精确匹配用
   - `compact_requested = _compact_filename(filename)` —— 去空白匹配用
   - `compact_match = None` —— 精确匹配失败时的兜底结果
4. **遍历**：`for root, dirs, files in os.walk(user_home):`（加剪枝，见 3.6）。
5. **精确命中立刻返回**：
   ```
   if file.casefold() == requested:
       return {"success": True, "filename": filename,
               "file_path": os.path.abspath(os.path.join(root, file))}
   ```
   为什么"立刻返回"：用户主目录里同名文件极少，第一个就是它。继续遍历是浪费。
6. **去空白匹配只记第一个**：
   ```
   if compact_match is None and _compact_filename(file) == compact_requested:
       compact_match = os.path.abspath(os.path.join(root, file))
   ```
   为什么只记不返回：精确匹配可能在后面的目录里出现，精确优先。
7. **遍历结束后**：`if compact_match: return {...}`。
8. **都没有** → `{"success": False, "filename": filename, "file_path": None, "error": "没有找到指定的 Aspen 文件"}`。

**坑**：

- 第 5 步**必须**在 `os.walk` 的双层循环内部 `return`，不是 break 出去再判断。
- `compact_match` 用 `is None` 判断，不能用 `if not compact_match`——空字符串也是 falsy，虽然路径不可能是空串，但习惯要统一。
- 加了剪枝后，**`dirs[:] = ...` 一定要原地改**（见 3.6）。
- 返回的 `filename` 是**用户输入值**，不是磁盘上的真实文件名。去空白匹配命中的情况下两者不同（`"10万吨 环己烷.bkp"` vs `"10万吨环己烷.bkp"`），模型如果拿 `filename` 再去拼路径会出错——**它应该只用 `file_path`**。这一点建议在 docstring 里写明。
